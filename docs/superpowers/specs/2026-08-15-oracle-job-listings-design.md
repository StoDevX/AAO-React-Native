# Student work listings from Oracle Recruiting

Fixes [#7759](https://github.com/StoDevX/AAO-React-Native/issues/7759). St. Olaf moved
student job postings to Oracle Recruiting Cloud, so the app's `/jobs` endpoint returns
nothing and the Student Work screen is empty.

## The Oracle API

Oracle Fusion HCM serves the same REST resources the Candidate Experience site calls, and
St. Olaf's tenant answers them without authentication. Verified live on 2026-08-15.

**Base:** `https://fa-ewur-saasfaprod1.fa.ocs.oraclecloud.com`

**List** — `GET /hcmRestApi/resources/latest/recruitingCEJobRequisitions`

- `onlyData=true`
- `expand=requisitionList,categoriesFacet`
- `finder=findReqs;siteNumber=CX_1,facetsList=CATEGORIES,limit=200,sortBy=POSTING_DATES_DESC`
- optional `selectedCategoriesFacet=<id>` inside the finder, to filter to one category

Returns one item holding `TotalJobsCount`, a `categoriesFacet` array of
`{Id, Name, TotalCount}`, and a `requisitionList` whose entries carry only `Id`, `Title`,
`PostedDate`, `PrimaryLocation`, `PrimaryLocationCountry`, and internal ids. No category,
department, wage, or description.

**Detail** — `GET /hcmRestApi/resources/latest/recruitingCEJobRequisitionDetails`

- `onlyData=true`, `expand=all`
- `finder=ById;Id=<id>,siteNumber=CX_1`

Adds `Category`, `RequisitionType`, `JobSchedule`, `ExternalPostedStartDate`,
`ExternalPostedEndDate`, and `ExternalDescriptionStr`.

**Web page for a job** — `/hcmUI/CandidateExperience/en/sites/CX_1/job/<id>`. This is both
the share target and the apply path.

### What the API will not give us

- **No batch detail fetch.** A multi-id finder (`Id=2841;2770`) returns an empty
  collection, so enriching list rows costs one request per job.
- **No contact details.** `ExternalContactName` and `ExternalContactEmail` were empty on
  all 16 postings sampled. The description names a supervising role, not an address.
- **Most of the old `JobType` does not exist as fields.** `hoursPerWeek`, `skills`,
  `timeline`, `openPositions`, and `goodForIncomingStudents` live, when they live at all,
  as bold-labelled paragraphs inside the description HTML.
- **Gzip regardless of `Accept-Encoding`.** `fetch` handles this; a raw curl needs
  `--compressed`.

### Shape of the data today

56 postings: 55 "Student Work", 1 "Summer Student Work". The whole `CX_1` site is student
work, so the categories map onto the section headers the screen already has.

Every description is generated by the same editor: `<p><span
style="font-weight:700">Label:</span><span>value</span></p>`, with zero `<b>` or
`<strong>` tags across the sample. Label frequency over 16 postings:

| Label | Present |
|---|---|
| Job Title, Classification, Department Name, Unit Number, Length of Position, Contact Person/Supervisor, Wage Range | 16 |
| Name and Address of Employer | 14 |
| Transferable Skills, Duties and Responsibilities | 11 |
| Description of the Position, Qualifications, Physical and Environmental Factors | 10 |

Two postings prefix their headings with roman numerals (`I. Description of the Position`),
and one uses `Description/Purpose of the Position`.

## Architecture

### `modules/ccc-jobs` (`@frogpond/ccc-jobs`)

A new client-side module mirroring `ccc-calendar`: `index.tsx`, `query.ts`, `types.ts`,
`parsers/`, `__tests__/`. Fetching, types, and parsing live here.
`source/features/sis/student-work/` keeps only the screen-side pieces (`job-row.tsx`,
`lib.ts`).

The app stops calling ccc-server's `jobs` endpoint. There is no fallback to it, because it
serves data the college no longer maintains.

### Manifest wiring

Add `REL_JOBS = 'https://frogpond.tech/rel/jobs'` to `@frogpond/data-sources`, and one link
to `data/sources.yaml`:

```yaml
- rel: https://frogpond.tech/rel/jobs
  href: 'https://fa-ewur-saasfaprod1.fa.ocs.oraclecloud.com/hcmUI/CandidateExperience/en/sites/CX_1'
  type: application/vnd.oracle.recruiting-ce+json
  titles: {und: Student Work}
  properties: {'https://frogpond.tech/ns/id': stolaf}
```

`data/sources.yaml` is the single source for the manifest. `scripts/build-sources.mjs`,
run by `mise run bundle-data`, emits both `modules/data-sources/bundled.json` and the
served `docs/sources.json` from it, so neither is edited by hand.

The href is the public site URL rather than the REST base, because everything we need
derives from it: the API origin, the `siteNumber` (its last path segment), and the per-job
web URL. One string to change if the tenant moves.

Jobs differs from calendar in one way. `fetchSourceBody` does a plain GET of a document,
but Oracle is a two-endpoint API with constructed `finder` queries. So `ccc-jobs` builds
its own requests and the manifest supplies only the site; `type` identifies which API
dialect the module is talking to, and `resolveSource`'s existing rules still apply.

### Requests

**List:** one call for `categoriesFacet`, then one call per category with
`selectedCategoriesFacet=<id>`. Three calls today, and it adjusts on its own if HR adds a
category.

**Detail:** one call per job, on tap, keyed by requisition id.

### Failure modes

- Unreachable or malformed manifest falls back to the bundled copy, as today.
- A failed list call surfaces the existing `NoticeView` with retry.
- A failed detail call gets the same, scoped to the detail screen.
- Zero requisitions uses the existing "There are no open job postings." empty state.

## Parsers

### `parsers/requisitions.ts`

Validates the list response with zod and returns
`JobSummary {id, title, postedDate, location, categoryId, categoryName}`.

### `parsers/description.ts`

Walks the description's block elements. A block whose first element is a
`font-weight:700` span ending in `:` yields `{label, value}`. Labels match
case-insensitively after stripping a leading roman numeral, which covers the variant
postings. Five labels are promoted to cells and removed from the rendered body:

| Label | Shown as |
|---|---|
| Department Name | Department |
| Wage Range | Wage |
| Length of Position | Length |
| Contact Person/Supervisor | Contact |
| Classification | Classification |

Three reliable labels are dropped outright, as useless to a student: *Job Title*
(duplicates the requisition title), *Unit Number* (HR accounting), and *Name and Address of
Employer* (the same college address every time). Every other block stays, in its original
order, as the body.

The scraper degrades rather than fails: a label it cannot find means one missing cell, and
a description that matches nothing becomes the body whole.

### `htmlToMarkdown` in `@frogpond/html-lib`

The body renders through `@frogpond/markdown`, so the kept blocks convert to markdown
first. `@frogpond/html-lib` already owns HTML parsing and its htmlparser2 DOM, so the
converter lives there: `htmlToMarkdown(html)` and `nodeToMarkdown(node)`.

Handing the raw HTML to the markdown renderer instead is not an option — md4c passes
unknown tags through, so students would read `<span style="font-weight:700">`. A
third-party converter is not one either: turndown needs a real DOM (it ships domino for
Node), which this app does not have and should not bundle for eight tag types.

The converter covers what these descriptions actually contain — `p`, `div`, `br`, `ul`,
`ol`, `li`, `a`, and the `font-weight:700` spans that stand in for `<strong>` — and escapes
markdown punctuation in text so a `*` or `_` in a posting renders literally.

## Screens

### List

Sections by category ("Student Work", "Summer Student Work"), each row showing title and
posted date. Department and wage are not in the list response and appear on the detail
screen instead.

### Detail

A SwiftUI `Form` from `@expo/ui/swift-ui`, following `source/features/map/building-info.tsx`:

1. A section of real Oracle fields: title, category, `JobSchedule`, `PrimaryLocation`,
   posted date.
2. A section of the five scraped fields, each row omitted when its label is absent.
3. The body, as markdown, in an `RNHostView matchContents` so the native
   `@frogpond/markdown` view sizes itself inside the Form.
4. A "View on the St. Olaf jobs site" button opening `{site href}/job/{id}`; the share
   action uses the same URL.

The email and phone cells go away — no address exists in the data to put in them. New date
formatting uses `date-fns`, not the `moment` import the current screen carries.

Two `@expo/ui` hazards apply. A bare string in a `ReactNode` prop crashes at mount, which
neither tsc nor Jest catches, so every string goes inside a `<Text>`. And ported rows
become buttons in the accessibility tree, so any UI test assertions come from dumping the
real tree rather than from guessing.

## Types

`JobType` is replaced by `JobSummary` and `JobDetail` in the module. Nothing outside
`source/features/sis/student-work/` and `app/(home)/JobDetail.tsx` imports it.

## Testing

Written test-first, in `ccc-calendar`'s layout and style.

Fixtures captured from the live API and committed under `__tests__/fixtures/`: a full list
response, the categories facet, and four detail responses covering the variation found —
the standard template, the roman-numeral variant, one missing *Description of the
Position*, and the single Summer Student Work posting.

Parser tests assert:

- the promoted labels parse to the right values
- an absent label yields no cell rather than an empty one
- a promoted label is not also left in the body
- an unrecognised description shape still becomes the body whole
- the list parser rejects a malformed response rather than yielding partial rows

`htmlToMarkdown` is tested in `@frogpond/html-lib` against each tag it supports, nested
lists, and markdown punctuation appearing in text.

## Companion change: ccc-server

Not in this repo, and not checked out locally yet.

`/jobs` returns a single legacy-shaped job so older installs show one clear row instead of
an empty list: title along the lines of "Student job listings have moved", `office` and
`type` filled so it groups sanely, and a description explaining that the college moved to
Oracle and that the listing lives in an updated version of the app.
