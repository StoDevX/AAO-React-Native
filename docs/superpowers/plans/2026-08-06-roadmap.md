# Roadmap: CNG migration, SwiftUI adoption, and tooling

The Phase A and Phase B plans were written before any of this ran. Both are now
partly wrong: Phase B's Task 1 assumed three module swaps in one PR, and neither
plan anticipated the SwiftUI work or the tooling change. This is the current
shape of the work; the older plans stay for their step-by-step detail, but where
they disagree with this file, this file is right.

Two tracks run in parallel. The CNG track is the original goal — generate `ios/`
from `app.config.ts`. The UI track came out of Phase B discovering that React
Native views hosted inside SwiftUI (`RNHostView`) are measured and exposed to the
accessibility tree differently, which makes them both visually wrong and
untestable. The fix is to stop crossing that boundary.

## CNG track

### B1.3 — finish removing the context-menu stack

Port the remaining consumers to `@expo/ui/swift-ui` and delete the wrapper
outright rather than reducing it to a shim: `@expo/ui` is already declarative, so
a shim would mostly forward props, and the wrapper's one non-obvious rule (an
action carrying `state` renders as a SwiftUI `Toggle`, everything else as a
`Button`) is clearer stated per call site.

- `source/views/transportation/bus/components/day-picker.tsx` — the only
  `selectedAction` consumer, so the only one on the `Toggle` path. Do it first.
- `source/views/reddit/post-detail.tsx` and `source/views/reddit/index.tsx`
- `source/views/settings/screens/overview/component-library/context-menu.tsx`
- Delete `modules/context-menu/` (a workspace package, so also drop it from the
  `workspaces` glob and from consumers' `package.json`)
- Drop `react-native-ios-context-menu`, `react-native-ios-utilities`,
  `contrib/0005`, `contrib/0006` and their sentinels in `scripts/apply-patches.sh`
- Remove the `react-native-ios-context-menu` entry from `tsconfig.json`'s `paths`
- Add UITests for the day-picker and reddit menus, neither of which has any
  coverage today

Each trigger must be SwiftUI-native rather than hosting React Native views, and
must carry `accessibilityIdentifier` — a `testID` does not reach the
accessibility tree from inside a SwiftUI host.

Payoff: five pods and the last two contrib patches.

### B1.4 — the self-contained community components

`@expo/ui`'s components split in two. Self-contained ones render their own
content and never host React Native views, so they avoid the boundary entirely;
container ones wrap app content and do not. These two are self-contained:

- `@react-native-picker/picker` → `@expo/ui/community/picker`. One consumer,
  `modules/filter/section-picker.tsx`.
- `@react-native-community/datetimepicker` → `@expo/ui/community/datetime-picker`,
  behind `@frogpond/datepicker`. Expo's API is `value`/`onChange`; ours is
  `initialDate`/`onDateChange`.

Neither has UITest coverage; add it before porting.

Payoff: `RNCPicker` and `RNDateTimePicker`.

Leave `react-native-popover-view` alone — it is a container component and will
hit the same boundary until its screens are SwiftUI.

### B2 — `app.config.ts` and config plugins

Unchanged from the Phase B plan. Scaffolding only; `ios/` stays authoritative.

### B3 — the prebuild cutover

Unchanged in intent, with two corrections found while running Phase B:

- The plan's build command pipes through `xcbeautify`, which is CI-only. On a dev
  machine the pipe fails and reads as a build failure.
- The plan omits the bundle-injection step. CI builds with `SKIP_BUNDLING=true`
  and then copies `main.jsbundle` and `ios/assets/` into the `.app`; the app
  prefers that injected bundle and only falls back to Metro. Without it the
  UITests run against whatever Metro happens to be serving.

## UI track

### Phase C — Settings to SwiftUI

Rebuild the Settings screens on `@expo/ui/swift-ui`'s `Form`, `Section`,
`LabeledContent`, `DisclosureGroup` and `Toggle`, replacing
`react-native-tableview-simple` and `@frogpond/tableview` on those screens.

Use the `swift-ui` exports rather than the `universal` ones. `universal`'s value
is cross-platform abstraction and this app is iOS only, so it buys nothing here;
`swift-ui` maps close to one-for-one onto the Swift an eventual native port would
write, including the modifier chains.

Settings is the right second screen: it is the most table-heavy, and
`ModuleSettingsTests` already exists, so there is a regression gate from the
start.

**This removes no pods.** `react-native-tableview-simple` is JavaScript only. The
justification is native feel and testability, not CNG surface.

Open questions to answer from the source before scoping:

- Can `Section` children be arbitrary React Native content? If so the
  `RNHostView` boundary returns and the screens must go SwiftUI wholesale.
- Does `Form` need `accessibilityIdentifier` for `ModuleSettingsTests` to keep
  passing, as the home screen did?

## Tooling track

### Phase D — npm to pnpm

Motivation is dependency ergonomics. Two problems in the current tree show why:

- `@expo/ui` hard-depends on `vaul`, a web drawer library, and declares
  `react-dom` an *optional* peer while `vaul` requires it non-optionally. npm
  installed `react-dom@19.2.8`, which peer-demands `react@19.2.8` against our
  pinned `19.2.3`, and the install failed with ERESOLVE. The workaround is a
  `file:` override pointing `vaul` at `stubs/vaul` — 27 packages removed, and
  `react-dom` with them.
- `min-release-age` in a developer's `~/.npmrc` silently caps every version
  choice, including security fixes, and produces `ETARGET ... with a date before
  <date>` from commands that look unrelated.

pnpm addresses the first directly: strict `node_modules` means a package cannot
use a dependency it did not declare, `pnpm.overrides` and
`pnpm.packageExtensions` express this kind of correction as intent rather than as
a stub package, and `onlyBuiltDependencies` replaces the blunt
`ignore-scripts=true` currently in `.npmrc`.

Scope:

- `package-lock.json` → `pnpm-lock.yaml`; `workspaces` → `pnpm-workspace.yaml`
  (33 packages under `modules/`)
- `npm ci` → `pnpm install --frozen-lockfile` in `.mise.toml`, four GitHub
  workflows (`check`, `build-and-deploy`, `cocoapods`, `deploy-data`), and
  `ci_scripts/ci_post_clone.sh`
- Replace the `vaul` stub with `pnpm.packageExtensions` marking `react-dom`
  optional where it belongs
- Keep `mise run prepare` wired to `pnpm install`'s lifecycle, since
  `contrib/*.patch` must still apply — pnpm has `patchedDependencies`, which may
  replace `contrib/` and `scripts/apply-patches.sh` entirely. Worth evaluating.
- CocoaPods reads `node_modules` paths directly; pnpm's symlinked layout needs
  checking against `use_expo_modules!` and the RN podspec resolution, and
  `node-linker=hoisted` is the fallback if it does not work

Sequence this after the CNG cutover. Changing the package manager and the native
build generation at once would make any breakage ambiguous.
