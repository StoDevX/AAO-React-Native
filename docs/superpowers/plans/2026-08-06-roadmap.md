# Roadmap: CNG migration, SwiftUI adoption, and tooling

The Phase A and Phase B plans were written before any of this ran, and both are
now partly wrong. Where they disagree with this file, this file is right; they
stay for their step-by-step detail.

Two tracks run in parallel. The **CNG track** is the original goal: generate
`ios/` from `app.config.ts`. The **UI track** came out of Phase B discovering
that React Native views hosted inside SwiftUI (`RNHostView`) are measured and
exposed to the accessibility tree differently, which makes them both visually
wrong and untestable. The fix is to stop crossing that boundary.

## What we learned the hard way

These cost real time. They are here so the next session does not re-derive them.

### SwiftUI hit regions do not follow a background

SwiftUI hit-tests a control's *content*. A fill drawn with `background()` is
decoration, and a `Button`'s region comes from its **label**, not from modifiers
applied to the `Button`. Five controls shipped with `padding`/`background` and no
`contentShape`, so each responded only where it had content — the home tiles on
the icon and title, the notice on its text, the bus day picker on its icon and
label, the reddit triggers on their glyphs.

**Every ported control needs `contentShape`, applied to the label for a
`Button`.**

**Our tests could not see this.** XCUITest taps the centre of an element's
accessibility frame; the frame reported the full coloured rect while only its
centre was live, so 26 tests passed over a home screen where most of every button
was dead. `testTileIsTappableAwayFromItsCentre` taps at a normalised
`(0.9, 0.15)` — the top-right, empty in every tile because the icon is centred
and narrow, where a long title like "Building Hours" fills the lower width.
**Any future SwiftUI port needs an equivalent off-centre tap.**

### Write characterisation tests against the old implementation first

Porting the context menus, tests written *after* the port would have asserted
whatever the port happened to do. Written against `react-native-ios-context-menu`
first, they caught a real regression: the component library passes no
`selectedAction`, so the old menu drew no checkmark, but the port rendered
`Toggle`s and added one.

### Same prop name, different meaning

`@expo/ui` maps `display` onto SwiftUI's `datePickerStyle`, so `"inline"` becomes
`graphical` — the calendar picker — where
`@react-native-community/datetimepicker` treated it as the inline time field.
Type checking passes either way. Assume nothing transfers by name alone.

### Test isolation

`UITestCase` now launches every test with `--reset-state`. Without it,
`UserDefaults` and AsyncStorage carried between tests, so
`testLongPressNoticeTogglesDevMode` inverted and failed whenever dev mode was
already on — passing alone, failing in long runs.

### Environment traps

- **Top-level await does not survive Metro.** `export const x = await …` fails to
  bundle. Resolve at startup into a module variable instead, and mind that
  anything read during module evaluation (`source/init/*`) will still see `null`.
- **`xcbeautify` is CI-only.** Piping a local build through it looks like a build
  failure.
- **Debug builds contain no JavaScript.** Inject `main.jsbundle` *and*
  `ios/assets/` into the `.app`, as CI does. See the `build-to-device` skill.
- **Keep derived data at exactly `ios/build`.** Any other name makes a later
  `pod install` parse a built app's binary Info.plist and fail with an opaque
  UTF-8 error.
- **Never mutate `node_modules`, `ios/Pods`, or the branch while a build or test
  runs.** Several convincing but fake failures came from this.
- **Run `npm ci` after every branch switch.** A tree from one branch with another
  branch's dependencies produces type errors that look like real bugs.
- **The cocoapods bot rewrites `Podfile.lock` checksums** on each pushed branch
  independently, which breaks a stack's ancestry every time we force-push.
- **`min-release-age` in `~/.npmrc`** silently caps version choices, including
  security fixes; `--min-release-age=0` is the agreed exception.

### npm cannot express the `vaul` stub

`@expo/ui` hard-depends on `vaul`, a web drawer library used only by its web
`BottomSheet`, and declares `react-dom` an *optional* peer while `vaul` requires
it. Three attempts to stub it all failed: a `file:` override resolves relative to
the overridden package and breaks `npm ci`; a workspace named `vaul` hits
ERESOLVE; an `npm:` alias to a workspace 404s against the registry. The
`react-dom: 19.2.3` override stays until Phase D.

## CNG track

### B2 — `app.config.ts` and config plugins

Unchanged from the Phase B plan. Scaffolding only; `ios/` stays authoritative.

Note `expo-build-properties` is **build-time only** — a config plugin, no runtime
API. It cannot report debug vs production.

### B3 — the prebuild cutover

Two corrections to the Phase B plan, both found by running it:

- Its build command pipes through `xcbeautify`, which is CI-only.
- It omits the bundle-injection step. CI builds with `SKIP_BUNDLING=true` and
  then copies `main.jsbundle` and `ios/assets/` into the `.app`; the app prefers
  that injected bundle and only falls back to Metro. Without this the UITests run
  against whatever Metro happens to be serving.

### After B2 — app variants

`app.config.ts` can vary bundle identifier, name and icon per variant, so a dev
build stops replacing the real app on a device. `Application.applicationId` then
identifies the variant synchronously.

That is also the better answer for build-type detection than today's
`IS_PRODUCTION` (bundle mode) and `isDebugBuild` (bundle mode plus prerelease
tags parsed out of the package.json version).
`Application.getIosApplicationReleaseTypeAsync()` reports the real provisioning
type — `DEVELOPMENT`, `AD_HOC`, `APP_STORE` — but it is async, and the two
`source/init/*` consumers run during module evaluation, so they must keep the
synchronous signal.

### Version reporting cleanup (small, independent)

`@frogpond/constants` takes its version from **package.json**;
`expo-application` reads the **native bundle**. `appBuild()` returns the part
after `+` in the package.json version, which has no `+`, so it is **always
undefined** — the Settings version cell has never shown a build number, while
`expo-application` reports the real one.

`@frogpond/constants` cannot be removed: `timezone` has 51 consumers,
`IS_PRODUCTION` 3, `isDebugBuild` 2. But `appName`, `isBeta`, `isAlpha`, `isPre`,
`isRc` and `userAgent` have **none** and should go.

Careful with `source/views/faqs/conditions.ts`: it does semver targeting of FAQ
banners against `appVersion()`, so switching it to the native version changes
which builds a remotely-driven banner targets.

## UI track

### Phase C — Settings to SwiftUI

Rebuild the Settings screens on `@expo/ui/swift-ui`'s `Form`, `Section`,
`LabeledContent`, `DisclosureGroup` and `Toggle`, replacing
`react-native-tableview-simple` on those screens.

Use `swift-ui`, not `universal`. `universal` is reachable from the package root
and does include `FieldGroup`, but it buys cross-platform abstraction this
iOS-only app does not need, and `swift-ui` maps close to one-for-one onto the
Swift an eventual native port would write.

Settings is the right second screen: it is the most table-heavy, and
`ModuleSettingsTests` already exists.

**This removes no pods** — `react-native-tableview-simple` is JavaScript only.
The justification is native feel and testability.

Open questions to answer from the source first: can `Section` children be
arbitrary React Native content (if so the `RNHostView` boundary returns), and
does `Form` need `accessibilityIdentifier` for `ModuleSettingsTests` to keep
passing, as the home screen did.

## Tooling track

### Phase D — npm to pnpm

Motivated by the `vaul` episode above: pnpm expresses that correction as intent
(`packageExtensions` marking `react-dom` optional where it belongs) rather than
as a stub package, and `onlyBuiltDependencies` replaces the blunt
`ignore-scripts=true` in `.npmrc`.

Scope: `package-lock.json` → `pnpm-lock.yaml`; `workspaces` →
`pnpm-workspace.yaml` (33 packages under `modules/`); `npm ci` →
`pnpm install --frozen-lockfile` in `.mise.toml`, four GitHub workflows and
`ci_scripts/ci_post_clone.sh`.

Two risks: **CocoaPods reads `node_modules` paths directly**, so pnpm's symlinked
layout needs checking against `use_expo_modules!` (`node-linker=hoisted` is the
fallback); and pnpm's `patchedDependencies` may replace `contrib/` and
`scripts/apply-patches.sh` entirely, which is worth evaluating rather than
porting them as-is.

Sequence after the CNG cutover: changing the package manager and the native build
generation at once would make any breakage ambiguous.

### Version control — Jujutsu

The main checkout is already a colocated jj repo (`.git` and `.jj`, one
`default` workspace). This work happened in a plain linked git worktree, so it
used git throughout, and roughly a third of the session's tool calls went on
rebasing the stack, repairing cocoapods-bot ancestry breaks, and fixing
branch/`node_modules` mismatches.

Move to jj for stack management: `jj git import` so it sees these branches as
bookmarks, then `jj workspace add` rather than `jj git init --colocate` inside a
linked git worktree. `jj rebase -d` restacks descendants automatically, which is
the churn being paid for now.
